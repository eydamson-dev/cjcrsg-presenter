# Media CPU cost — 2026-11-09

DEV-010: the dropped-frame measurement said nothing about what video costs. This
is that number, measured on the whole process tree.

## Method

- The real app, four output windows (`CJCRSG_DEMO_OPEN=all`), one 10-minute
  1080p30 VP9 clip from the loopback media server.
- Preview shows the next slide (a still), so **three** surfaces decode live
  video: Audience, Stage (muted), Confidence.
- `parity/tools/measure_process_tree.py` samples `/proc` for the main process
  and every descendant — WebKit spawns several — over 60 seconds after a 12 s
  warm-up, and reports CPU as `(utime+stime) / elapsed`.
- Debug build of the Rust shell; decoding happens in WebKit, not in our code.
- Fedora 44, KDE/Wayland, Ryzen 5 5600X (6 cores / 12 threads), RTX 5060 Ti,
  WebKitGTK software VP9 decode.

## Numbers

```json
{
  "seconds": 60.0,
  "cpu_percent": 112.6,
  "rss_mb": 2204.6,
  "process_count": 14,
  "processes": ["cjcrsg-presente", "WebKitWebProces" x5, "WebKitNetworkPr" x5, "bwrap" x2, "glycin-svg"]
}
```

- **112.6 % of one core**, i.e. ~1.13 cores.
- **9.4 % of the machine's 12 logical CPUs.**
- **2.2 GB RSS** across 14 processes.
- No dropped frames in the same configuration over 10 minutes
  (`media-four-outputs-2026-11-09.md`).

Against Experiment 3's criterion, "CPU, four windows, 1080p < 60 % of the
machine": 9.4 % of total capacity, comfortably inside it.

## What this does not prove

- **Software decode.** WebKitGTK is decoding VP9 on the CPU here. Whether a GPU
  path engaged was not checked; with hardware decode the number would be lower.
- **VP9, not H.264**, and **WebKitGTK, not WebView2**. Windows is unmeasured.
- **Three surfaces, not four.** Preview is a still by design; the 30-second
  four-decoder run predates that change and has no CPU figure.
- **Debug build.** The Rust shell costs little either way, but this is not a
  release-build number.
- **No per-process split.** The report lists process names, not their individual
  CPU shares.
