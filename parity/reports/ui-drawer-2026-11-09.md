# Controller drawer — implementation report (DEV-013, milestone 1)

Date: 2026-11-09
Contract: `docs/contracts/ui-drawer.md` (approved 2026-11-09)
Scenarios: `parity/scenarios/controller-drawer.yaml`
Reference: FreeShow `ff784eb388c7baef60d67e6d4e7c504f4322bca3` (1.6.8-beta.3)

Status: **candidate ready for verification.** This report does not accept the
work; the verifier grades the exact commit.

## What was built

- A bottom drawer below the three columns, spanning the window, with the 40 px
  tab strip, a scrolling content area and a 290 px right-hand clock column.
- Eight tabs in FreeShow's order and labels, with the digit as the Ctrl hint:
  `1 Shows` … `8 Functions`. The active tab has a 2 px accent underline and a
  lighter background. The strip scrolls horizontally, never wraps, and labels
  are never hidden (DEV-014).
- **Shows**: one row per project show, with the name, slide count, live marker
  and a Play button using the same `go_to_show` command as the outline.
- **Media** and **Audio**: the existing read-only media list, split by
  `MediaKind::Audio`, with kind, origin, size, tags and `missing`. The old centre
  column list was removed, so the controller renders exactly one copy.
- **Overlays, Templates, Scripture, Calendar, Functions**: the tab's name and one
  sentence stating why it is empty (B10), not a blank panel or a disabled
  control.
- Collapse (40), default open (300), drag-to-resize with the 80 px collapse
  threshold, strip-background toggle, double-click-tab collapse, and opening a
  collapsed drawer to the remembered open height. A pointerdown anywhere on the
  strip—including over a tab or the 4 px bar—starts a potential drag; the
  following click is suppressed only when the pointer moved, and the grab offset
  is preserved.
- The remembered open height is in `core::session::LayoutPrefs`, with
  `serde(default)` for old sessions, clamped to 40..=1200 on read, floored to
  300 when reopening, and finally clamped to the space below the measured top
  bar (B1, 744 px at an 800 px window).
- Ctrl+1..8 in `apps/desktop/assets/keys.js`, ignored while typing in an
  `input`, `textarea` or `select`.
- A page-local `document::eval` clock: `HH:mm:ss`, 24-hour, accent-coloured and
  centred, with a long-form weekday date underneath, updating every 500 ms.

### Grab bar and grab offset

`drag-hit-test-probe.mjs` loads the shipped `main.css` and `DRAWER_SCRIPT` in
headless Chromium and uses real Playwright mouse input, not a synthetic pointer
dispatched at a hand-picked element. `drag-hit-test-report.json` records:

- at 1280×800, 1024×640 and 400×600, the point 2 px below the drawer top at the
  horizontal centre hits `BUTTON.drawer-tab`; a real mouse press and drag there
  sends a `drawer_resize` (heights 502/342/302 in the probe). A press at x=40
  over the active tab does too, and so does the empty strip. This is the D1 fix:
  the button no longer blocks the drag.
- a press/release on the tab with no movement still fires its click (probe
  count 1) and selects the tab; a press with a pointermove suppresses it (probe
  count 0). Only a pointermove sets the suppression, so a click is not lost.
- grabbing the strip 2 px below its top and moving the pointer 2 px up changes
  the drawer from 300 to 302 and leaves the pointer exactly 2 px below the new
  top. The offset is preserved (D5); a drag does not teleport the edge to the
  pointer. The app-level `drag:744`/`drag:520` captures use the same offset
  arithmetic and an `elementFromPoint` hit at the bar centre.

The 1280×1400 content-box half of the clamp-high scenario is not reachable on
this machine: the window manager caps the client at 1329 px tall (WebView 1302)
on the 4480×1440 display. The 1280×1302 capture shows the 1200 session clamp
against a 1246 maximum; the 800 captures show the window maximum. The 1400
value is not asserted.

The drag was driven through the real pointer handlers (`pointerdown` /
`pointermove` / `pointerup`) because synthetic X11 pointer events are not
delivered to an XWayland WebView. The app-level hook uses a real
`document.elementFromPoint` hit at the bar centre; the separate Playwright probe
uses real mouse input. The release is what writes the session; a held drag does
not (the JS updates a CSS custom property during the gesture, so Rust is not in
the pointer loop).

Reopening was also captured end to end: with a remembered 520, the app was
relaunched and the drawer opened at 520; selecting Media changed only the tab
(`drawer-reopened-520-1280x800.png`). The remembered-80 relaunch is the B5
counterpart: it opens at 300 without rewriting the stored 80.

### Side-by-side against FreeShow

`drawer-comparison-1280x800.png` stacks the same 300 px drawer from FreeShow
1.6.8 and this candidate, both at a 1280×800 window. The raw reference capture
is `freeshow-drawer-1280x800.png`. FreeShow's scratch profile had
`timeFormat: "12"`; it was set to `"24"` for the capture so the clock comparison
is like for like. Differences visible and named:

- **Left sub-column**: FreeShow has a 290 px category/sub-tab column; ours has
  none. Contract Scope: only one list per tab exists today.
- **Search**: FreeShow has a search field in the strip; ours has none. Out of
  scope in this milestone.
- **Icons and digits**: FreeShow shows icons with no digits; ours is text-only
  with the Ctrl digit as part of the label (B2, DEV-014).
- **Shows content**: FreeShow uses a Name/Modified table with Import/New show;
  ours is a simple row list with slide count, live marker and Play (B7). The
  reference's show rows are not the contract's rows.
- **Info column**: FreeShow swaps in a per-show/media info panel and falls back
  to the clock; ours always shows the clock because no info panels exist yet
  (B11).
- **Clock type**: both are 24-hour `HH:mm:ss`, accent-coloured, with the same
  long-form weekday date; FreeShow's clock is much larger (roughly 4 em) than
  our 36 px.
- **Palette, strip height, 300 px drawer and 290 px info column** match.

## Interpretations and limitations

1. **The merged contract/scenario amendment is implemented; the two previously
   stale B5 expectations were corrected upstream.** The candidate already
   reopened a remembered sub-300 height at 300 without rewriting the stored
   value; no product change was needed for that clarification.
2. **Synthetic X11 input does not reach the XWayland WebView.** For the
   app-level captures, a debug-build `CJCRSG_DRAWER` hook performs the same DOM
   clicks and pointer events through the real handlers; its drag action uses a
   real `document.elementFromPoint` hit at the bar centre, not a hand-picked
   empty-strip coordinate. The separate Playwright probe uses real mouse input.
   The hook is guarded by `cfg!(debug_assertions)` and is not part of the
   presentation path.
3. **400×600 narrow strip** could not be reached because the window's minimum
   inner size is 1024×640; measured at that minimum instead, as the scenario
   allows.
4. **FreeShow clock setting.** The scratch profile had `timeFormat: "12"`; it
   was changed to `"24"` in the scratch store for the comparison, because B11
   specifies 24-hour time.
5. **The scenario adapter/fixture gap (verifier D6) is unchanged.** There is
   still no controller adapter and the proposed content fixtures are not
   authored; this report does not invent a harness for them.

## Implementation notes

The maximum is measured, not assumed. The page reads
`.topbar.getBoundingClientRect().height` (56 px in the steady layout), sets
`--topbar-h`, and reports the same value to Rust; CSS, the drag script and the
Rust clamp therefore cannot disagree. At innerHeight 800 the maximum is 744.

The workspace is wrapped in an inner frame so its 12 px padding is part of the
scrollable region, not a minimum height that pushes a maximum-height drawer off
the bottom. At ordinary heights the columns look exactly as before; at the
maximum they have no height left, and the drawer fills the space below the top
bar.
